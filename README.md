# crawler-cli

CLI на Go, который обходит сайты по ссылкам и сохраняет дерево найденных страниц с их title в JSON.

Нужен Go 1.26+.

## Сборка и запуск

```bash
go build -o crawler-cli ./cmd/crawler-cli

./crawler-cli --urls https://go.dev,https://example.com --depth 2 --timeout 2m --request-timeout 10s
```

Можно и без сборки через `go run ./cmd/crawler-cli ...` с теми же флагами.

Флаги:

- `--urls` - стартовые адреса через запятую (обязательный)
- `--depth` - глубина обхода, минимум 1 (обязательный)
- `--timeout` - общее время работы, например `2m` (обязательный)
- `--request-timeout` - таймаут одного запроса, например `10s` (обязательный)
- `--output` - папка для результатов, по умолчанию `./out/result`
- `--log` - папка для логов, по умолчанию `./out/logs`

Обратите внимание, что `--output` и `--log` это папки, а не файлы. Сделано так, чтобы каждый запуск создавал новые файлы, а не перезаписывал старые. Имя файла это время запуска, например `2026-09-24T17-42-21.329333.json`, у лога такое же имя, только `.log`.

Если в URL есть `&`, адреса нужно взять в кавычки, иначе bash разрежет команду.

Остановить можно через Ctrl+C, то что успело обойтись все равно сохранится в JSON.

## Как работает

Есть один диспетчер и 10 воркеров, они общаются через два канала. Диспетчер держит очередь задач, список посещенных URL и само дерево, раздает задачи воркерам и собирает результаты. Воркер качает страницу, достает title и ссылки, выкидывает ссылки на чужие домены и отправляет результат обратно. Так как дерево и visited меняет только диспетчер, мьютексы не понадобились. Воркеров 10, каждый делает один запрос за раз, поэтому одновременно запросов не больше 10.

Обход заканчивается, когда в очереди пусто и ни один воркер ничего не обрабатывает. Общий таймаут и Ctrl+C отменяют общий контекст, от него же создается таймаут каждого запроса, так что при остановке прерываются и текущие запросы.

Структура:

```
cmd/crawler-cli   main: флаги, контексты, логгер, запись результата
internal/config   разбор и проверка флагов
internal/fetcher  HTTP запросы
internal/parser   парсинг HTML
internal/crawler  диспетчер и воркеры
```

## Решения

- Глубина считается как количество переходов. Стартовая страница это глубина 0, при `--depth 1` обходится стартовая страница и все ссылки с нее. Страницы на последнем уровне тоже запрашиваются (чтобы достать title), но их ссылки уже не обходятся.
- Домен сравнивается по хосту целиком, так что `www.site.com` и `site.com` считаются разными.
- URL сравниваются как есть, без нормализации, как сказано в задании. Из-за этого `https://go.dev` и `https://go.dev/` это две разные страницы. Единственное, что я отрезаю, это часть после `#`, иначе ссылки типа `#top` заставляли качать ту же страницу еще раз.
- Visited общий для всех стартовых URL. Если дать два адреса с одного сайта, одна страница не скачается дважды, но попадет только в одно дерево.
- Если на страницу ведут несколько ссылок, она окажется под той, которая обработалась первой. Порядок может меняться от запуска к запуску, корни тоже идут в порядке загрузки, а не как в `--urls`.
- Редиректы, не-HTML и страницы с ошибками в дерево не попадают, только в лог. Если не открылся ни один стартовый URL, в результате будет `[]`.
- Если какой-то URL в `--urls` невалидный, программа сразу выходит с ошибкой. Лишние запятые просто игнорируются.
- Страницы больше 5 МБ обрезаются, чтобы не съесть всю память.
- Запятую внутри URL передать нельзя, она считается разделителем.

## Логи

В логе на каждый запрос есть строка со статусом. Редиректы и не-HTML пишутся как INFO, потому что это нормальная ситуация по заданию. Настоящие ошибки (сеть, таймаут, 404, 500) пишутся как WARN, их удобно искать через `grep level=WARN`.

## Тесты

```bash
go test -race ./...
```

Есть unit тесты на конфиг, парсер, fetcher (через `httptest`), воркер и диспетчер (с фейками), и интеграционные тесты на весь обход на локальном тестовом сайте. В них проверяются домен, глубина, редиректы, циклы, таймаут и то, что одновременно идет не больше заданного числа запросов.
